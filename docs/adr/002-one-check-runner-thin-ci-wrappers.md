# ADR-002: One check runner, thin generated CI wrappers

## Status
Accepted

## Date
2026-10-09

## Context
The repo commits generated copies of `shared/` sources into skill folders, so something has to
prove those copies are fresh, that no machine path ships, and that every skill is registered.
Those checks have to run identically on a laptop and in whichever CI provider an adopting project
uses. (Source: `tests/verify.sh` header, `so-init/references/ci-templates.md`, AGENTS.md
"Required Checks".)

## Options Considered
1. **Write the checks into each provider's CI config** — every provider grows its own idea of
   "passing" and they drift.
2. **Ship one `.gitlab-ci.yml`** — one org's assumption imposed on every adopter.
3. **One runner, `tests/verify.sh`, plus a per-provider wrapper generated by `/so-init`** —
   chosen. The wrapper only checks out the repo and calls the runner.

## Decision
`tests/verify.sh` is the single source of check logic. CI configs are thin wrappers copied
verbatim from `so-init/references/ci-templates.md` for the detected git host. For this repo the
host is GitHub, so `.github/workflows/verify.yml` runs the same command on push and pull request.

## Consequences
Positive: a green local run is real evidence CI will pass; adding a check is one edit. Negative:
a provider the templates do not cover gets the manual command, not a config. Operational: the
`synced ->` output format of `build.sh` is parsed by the generated-copies guard, so it is a
contract (AGENTS.md, files requiring extra care).

## Validation
`./tests/verify.sh` exits 0 locally and the GitHub Actions run on the next push is green.
